# Part III — Project closure {.unnumbered}

# AI-assisted development

The professor set four requirements for the use of AI tools (P20–P23): an AI tooling
architecture, documented prompts and constraints, iterative refinement, and verification and
ownership of what the AI produced. This chapter reports what was done for each, and what the
record shows about the AI's mistakes.

## Tooling architecture

Table 3.3 (chapter 3) lists the tool for each phase. In short: the plan — the algorithms, the
backlog, the acceptance criteria and the UML inventory — was written before any code and approved
as the design. **Claude Code** then implemented one sprint at a time, from those algorithms and
criteria, inside the repository, with the quality gate as its checkpoint.

## Constraints: the rules file

`CLAUDE.md` is under version control and binds every AI tool used on the repository. It fixes the
stack and the folder layout, and nine rules:

1. never change `contracts/` without a recorded design decision;
2. write or update tests first, named with the story or NFR ID they prove;
3. take token rules only from `pathway-core`;
4. keep secrets, tokens and patient identifiers out of code and logs;
5. a docstring on every public function, cyclomatic complexity at most 10;
6. ruff, mypy --strict and pytest with coverage must pass;
7. every event handler is duplicate-safe and runs inside the case lock;
8. one story at a time, from its UML and acceptance tests, with the story ID in the commit;
9. code the author cannot explain is not merged.

Rules 1, 2, 5 and 6 were enforced mechanically on every increment: eight decisions were recorded
before contract changes, every test name carries an ID (appendix A), and the gate was run before
each tag. Rule 9 is a human rule; the presentation is where it is tested.

## Iterative refinement: the prompt log

Each sprint has a prompt log (`docs/ai-log/sprint-N.md`) with the goal, the prompt, what was
produced, what was kept or changed and why, the tests added, and a section titled "Where the AI was
wrong and the tests caught it". The prompts themselves were short — for most sprints, "continue",
or "start Sprint N: …" naming its stories — because the plan carried the specification: each
sprint's algorithms, acceptance criteria and UML were already written. In this project the
specification lived in the plan, not in the prompts.

## Verification: where the AI was wrong

The "Where the AI was wrong" sections of the eight logs record 31 defects in AI-produced code,
tests or documents, each found before its increment was tagged; Closure found two more (the
NFR-ROB-01 gap and a stale comment, `docs/ai-log/closure.md`). One further entry, in Sprint 6, was a
contradiction in the plan itself rather than an AI defect, and is not counted. Table 14.1
classifies the 33 by how they were found.

| Found by | Count | Examples |
|----------|------:|----------|
| Property-based tests | 3 | Unbounded tokens in loops hid duplicate work; TOO_LARGE hid real errors (Sprint 0); a generator broke a new rule (Sprint 2) |
| Fault-injection and replay tests | 1 | Replies correlated by long-lived token id (Sprint 3) |
| Acceptance tests | 2 | Undo order with ≤ vs < (Sprint 4); a fallback test that could never pass (Sprint 7) |
| Other unit and component tests | 11 | Edges without ids (Sprint 1); timezone-less timestamps (Sprint 2); NaN is truthy (Sprint 6); scrapes counted as traffic (Sprint 7) |
| Static checks (mypy, bandit) | 2 | A FastAPI-only decorator on a Starlette type; an empty password default (Sprint 7) |
| The running system or the browser | 7 | Invisible nodes; an unclickable branch (Sprint 1); a default trigger starting cases for every patient (Sprint 3); silent no-op edits (Sprint 4) |
| Reading the output or reviewing against the requirements | 7 | A test that proved nothing (Sprint 5); calibration undid the class weights (Sprint 6); an overclaim in a log (Sprint 7); NFR-ROB-01 (Closure) |

: Table 14.1 — Defects in AI-produced work, by how they were found (from `docs/ai-log/`).

Three lessons stand out.

1. **Tests prevent the AI's errors only when they can fail.** In Sprint 5 the AI wrote a
   priority-queue test that could not fail — the queue was hopelessly overloaded, so "urgent
   patients are served" held trivially. In Sprint 7 it wrote a fallback test whose premise was
   impossible, because nothing answers a request to an absent service. Both were caught because a
   human read *what the test proves*, not whether it passes.
2. **Some defects are visible only outside the unit tests.** Fourteen of the 33 were found in the
   browser, in the running stack, or by reading output against the requirements. The plan's "review in the running system"
   at every sprint was the cheapest effective check.
3. **The AI also makes documentation errors.** It claimed "no engine change" when `git diff` showed
   three lines, and it reported NFR-ROB-01 as met on a test that did not reproduce the requirement's
   situation. Claims in documents need the same checking as code.

## Ownership

The algorithms were specified in the plan before any code was generated: the verifier's pseudocode,
the engine's invariants and failure order, the simulator's statistics and validation. The code
follows those specifications, and every place where it departs from them has a decision record
(0001–0008) explaining why. That makes the generated logic explainable from the design rather than
from the code. Whether the author can explain every function is checked in the presentation;
`docs/closure/rehearsal.md` lists the questions the professor is likely to ask, with answers
grounded in the code.

## Assessment

The AI assistant made the planned scope feasible: 207 story points, three algorithms and eleven
services. It also compressed sixteen planned weeks into two days, which removed the calendar on
which Scrum's feedback loops depend: no burndown, no retrospective with time to act on it. The
written plan, the rules file, the tests and the decision records did the work that the calendar
would otherwise have done.
