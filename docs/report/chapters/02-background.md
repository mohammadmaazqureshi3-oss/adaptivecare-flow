# Background and related work

## Clinical pathways and emergency triage

A care pathway is "a complex intervention for the mutual decision-making and organisation of
care processes for a well-defined group of patients during a well-defined period" (European
Pathway Association, in [26]). In practice
it is a flowchart with roles, time limits and decision rules. Emergency triage is the classic
example: on arrival, a nurse measures vital signs and assigns an urgency level, which decides
how long the patient may wait. This project uses the five-level **Korean Triage and Acuity
Scale (KTAS)** because a public research dataset exists for it: Moon et al. [6] studied 1,267
emergency visits and found that nurses mistriaged 14.7% of them, mostly under-triage of urgent
patients. That figure motivates two design choices: the model is decision support only (a nurse
confirms every level), and the pathway's safety rules route patients with red flags to review
whatever the model says.

The **National Early Warning Score 2 (NEWS2)** of the Royal College of Physicians [7] is a
second, rule-based score: seven observations (respiration rate, oxygen saturation, supplemental
oxygen, systolic pressure, pulse, consciousness, temperature) each give 0–3 points, and a total
of 7 or more calls for an emergency response. It is used in Sprint 7 to show that a new task
type can be added as a service without changing the engine (CLN-04).

## Workflow languages, Petri nets and soundness

Workflow engines execute process models. The industry standard notation is **BPMN 2.0** [3];
UML activity diagrams have the same roots. The course slides (*7 – modeling*) state that activity
diagrams derive from "event diagrams, flowcharts and Petri nets". A **Petri net** consists of places,
transitions and tokens; a transition fires when each of its input places holds a token, consuming
them and producing tokens on its outputs [25]. The state of the net is its **marking**: the number
of tokens in each place.

Van der Aalst [1] mapped workflows onto Petri nets (*workflow nets*) and defined **soundness**:

- *option to complete* — from every reachable marking, the final marking can still be reached;
- *proper completion* — when the final place is marked, no other token remains;
- *no dead transitions* — every transition can fire in some reachable marking.

Soundness is decidable for workflow nets but expensive in general (state explosion); for the
block-structured, free-choice models typical of clinical pathways it is tractable [2]. This
project adopts these three properties for the control flow, adds **safeness** (no arc ever holds
two tokens, which in a pathway means a step would run twice for the same patient), and adds
**data soundness**: every variable a step reads is written on every path that reaches it, and
every branch condition type-checks. Algorithm 1 decides all five.

## Execution engines and why one was built

Mature engines exist. **Camunda** executes BPMN with a relational database and external task
workers; **Temporal** executes workflows written as code with durable, replayable history;
**Node-RED** is a low-code flow editor for event wiring. They were considered and not used, for
three reasons:

1. The professor's brief requires the workflow engine and IDE to be the student's own
   algorithmic work (requirements P3, P4, P10); wrapping Camunda would leave nothing to design.
2. None of them verifies a model before deployment in the sense above, and none simulates it
   with the *same* semantics it executes. Sharing one token-rule library among verifier,
   simulator and engine is the central idea of this project.
3. BPMN 2.0 is far larger than clinical pathways need. A small language with eight token rules
   can be verified exhaustively and explained in one page (chapter 7).

The engine's reliability techniques are standard and are credited as such: the **transactional
outbox** and idempotent consumers for at-least-once messaging [8, 19], **event sourcing** with
snapshots for recovery [19], and **sagas** — compensating finished steps in reverse order when a
long-running process fails [9]. The project's own design is the token interpreter that combines
them with per-case locking and wait-id correlation so that the invariants I1–I5 hold (chapter 9).

## Simulation and queueing theory

**Discrete-event simulation** advances a clock from event to event using a future-event list,
and estimates performance measures from independent replications, each reported as a mean with
a Student-t confidence interval [4]. Arrivals whose rate changes by the hour are generated by
**thinning** [12]: candidates are drawn at the peak rate and each is kept with probability
λ(t)/λ<sub>max</sub>.

Queueing theory gives exact answers for simple cases. For an **M/M/c** queue (Poisson arrivals,
exponential service, *c* servers) the probability of waiting is the **Erlang C** formula and the
mean wait is

$$W_q = \frac{C(c,a)}{c\mu-\lambda},\qquad C(c,a)=\frac{\frac{a^c}{c!}\frac{c}{c-a}}{\sum_{k=0}^{c-1}\frac{a^k}{k!}+\frac{a^c}{c!}\frac{c}{c-a}},\qquad a=\frac{\lambda}{\mu}.$$

**Little's law** [5], L = λW, holds for any stable system. Real pathways have parallel steps,
priorities, non-exponential durations and hourly arrival rates, for which no closed formula
exists. The simulator therefore uses the formulas only where they are exact: to validate itself
(chapter 11).

## Microservices and events

The course slides (*9 – sw architecture*) present the client-server, layered, repository,
implicit invocation, publish-subscribe, interpreter and service-oriented styles. The platform
uses all of them (chapter 5). The DevOps white paper motivates infrastructure as code (Docker
Compose), deployment automation, log management and monitoring. **Conway's law** [17] — a system's
structure mirrors its team's communication — is noted as a limitation: with a one-person team,
service boundaries follow capabilities rather than teams.

## Machine learning for triage

Urgency prediction from vital signs and complaint keywords is a standard supervised
classification task. Logistic regression, random forests and gradient boosting are reasonable
baselines [11]. Two properties matter more than raw accuracy: **calibration** (a predicted 70%
should be right 70% of the time; sigmoid calibration [22]) and **explanation** (which features
pushed the prediction; SHAP values [10]). Following the professor's rules, the model itself is a
*Category 2* feature (a library model); what the pathway does with its output — routing patients
through a decision executed by the engine — is the Category 3 part (requirement P11).
